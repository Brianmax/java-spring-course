Gimnasio: clases y reservas

Construye una API REST para administrar socios y reservas de clases grupales aplicando la misma arquitectura por capas del proyecto de clase. Ver enunciado en Markdown ↗.

Contexto del producto

PulsoFit es un gimnasio local que ofrece clases grupales de Spinning, Funcional, Yoga y Pilates. Hasta hoy, la recepción registra a los socios y apunta sus reservas en hojas de cálculo y mensajes de WhatsApp, lo que provoca dos problemas frecuentes: algunos socios acaparan demasiados cupos durante la semana sin asistir, y el personal no sabe con certeza cuántas reservas activas tiene cada miembro.

Tu tarea es construir la primera versión del backend REST que usarán el panel de recepción y la futura app móvil para:

  • Registrar socios sin duplicar DNI ni correo electrónico.
  • Crear reservas válidas y limitar a cada socio a un máximo de 4 reservas activas a la vez.
  • Consultar reservas generales o filtradas por socio, corregir el nombre de una clase y confirmar asistencias en recepción para liberar cupos automáticamente.

Lo que vas a practicar

  • Arquitectura en capas: controller, service, repository, entity y dto.
  • Endpoints REST con @RestController, @GetMapping, @PostMapping, @PatchMapping, @PathVariable, @RequestParam y @RequestBody.
  • Códigos HTTP con ResponseEntity (200 OK, 201 Created, 400 Bad Request, 404 Not Found).
  • Persistencia en PostgreSQL con entidades JPA, claves UUID y relación @ManyToOne / @OneToMany.
  • Reglas de negocio en el servicio: validaciones, unicidad, límite de reservas activas y confirmación de asistencia.

Configuración inicial

  1. Crea un proyecto Spring Boot con Java 21 y Maven usando como referencia Introducción a Spring Boot.
  2. Incluye las dependencias de Web MVC, Spring Data JPA, PostgreSQL y Lombok.
  3. Crea una base de datos llamada gimnasio en PostgreSQL y configura src/main/resources/application.properties:
spring.application.name=gimnasio

spring.datasource.url=jdbc:postgresql://localhost:5432/gimnasio
spring.datasource.username=postgres
spring.datasource.password=admin

spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
spring.jpa.hibernate.ddl-auto=update

No devuelvas entidades JPA directamente en los controladores. Crea DTOs separados (SocioRequest, SocioResponse, ReservaRequest y ReservaResponse) para controlar qué datos entran y salen de tu API.

DTOs sugeridos

  • SocioRequest: dni, email, nombre, apellido, edad.
  • SocioResponse: id, dni, email, nombre, apellido, edad, reservasActivas.
  • ReservaRequest: nombreClase, horario, fechaClase, socioId.
  • ReservaResponse: id, nombreClase, horario, fechaClase, asistio, socioId.

Endpoints y reglas de negocio

1. Socios (/api/v1/socio)

MétodoRutaDescripciónRespuestas
POST/api/v1/socio/saveRegistra un nuevo socio201, 400
  • dni, email, nombre y apellido son obligatorios y no pueden estar vacíos.
  • email debe contener @; normalízalo con trim().toLowerCase().
  • edad es opcional, pero si viene informada debe ser mayor o igual a 14.
  • Rechaza DNI o correo duplicado usando existsByDni y existsByEmail en SocioRepository.

2. Reservas (/api/v1/reserva)

MétodoRutaDescripciónRespuestas
POST/api/v1/reserva/saveCrea una reserva para un socio201, 400
GET/api/v1/reserva/findLista todas las reservas200
GET/api/v1/reserva/find/{id}Busca una reserva por su UUID200, 404
GET/api/v1/reserva/find-reservas-socio/{idSocio}Lista las reservas de un socio200, 404 / 400
PATCH/api/v1/reserva/confirmar-asistencia/{id}Confirma asistencia y reduce reservasActivas200, 400, 404
PATCH/api/v1/reserva/cambiar-clase/{id}?nuevoNombre=...Actualiza el nombre de la clase200, 400, 404
  1. Crear reserva: valida que nombreClase solo tenga letras, números y espacios (^[a-zA-Z0-9 ]+$), que horario no esté vacío, que fechaClase sea mayor o igual a la fecha actual y que el socio exista. Un socio puede tener como máximo 4 reservas activas (reservasActivas >= 4 se rechaza con 400). Al guardar, incrementa reservasActivas en +1.
  2. Buscar por ID: devuelve 200 OK con la reserva encontrada o 404 Not Found si no existe.
  3. Reservas por socio: verifica primero si el socio existe (existsById) y consulta sus reservas en ReservaRepository con una consulta personalizada @Query (por socio_id).
  4. Confirmar asistencia: si la reserva no existe devuelve 404. Si asistio ya era true, rechaza con 400 para evitar descontar dos veces. Marca asistio = true, resta 1 a reservasActivas del socio (sin bajar de 0) y guarda ambos cambios.
  5. Cambiar clase: valida nuevoNombre con ^[a-zA-Z0-9 ]+$ (si falla responde 400; si la reserva no existe responde 404), actualiza nombreClase y devuelve el DTO actualizado.

Ejemplos de peticiones JSON

Registrar un socio (POST /api/v1/socio/save)

{
  "dni": "72458910",
  "email": "camila.torres@correo.com",
  "nombre": "Camila",
  "apellido": "Torres",
  "edad": 24
}

Crear una reserva (POST /api/v1/reserva/save)

{
  "nombreClase": "Spinning Intermedio",
  "horario": "18:30",
  "fechaClase": "2026-12-10",
  "socioId": "c7c9a8d2-4d34-4b4e-8f52-91b7c54f1a20"
}

Cambiar el nombre de la clase

PATCH /api/v1/reserva/cambiar-clase/8a41f0b3-1c90-4a12-9b88-34e2a1d90f11?nuevoNombre=Yoga%20Matutino

Comprueba tu solución

  • Socios y unicidad: registra un socio válido (201). Repite el mismo DNI o email (400). Prueba con edad: 12 (400) y omitiendo edad (201).
  • Validaciones de reserva: intenta guardar una reserva con nombreClase: "CrossFit!!!" (400), con una fecha anterior a hoy (400) y con un socioId inexistente (400).
  • Límite de 4 reservas activas: crea 4 reservas para un mismo socio (201 en cada una y reservas_activas = 4). La quinta reserva debe responder 400.
  • Confirmar asistencia y liberar cupo: confirma asistencia en una de las 4 reservas (200, asistio: true y reservas_activas = 3). Vuelve a llamar al mismo endpoint con el mismo ID y comprueba que no vuelve a descontar. Luego registra una nueva reserva y verifica que ahora sí devuelve 201.
  • Consultas y edición: prueba GET /find, GET /find/{id} (existente e inexistente), GET /find-reservas-socio/{idSocio} y PATCH /cambiar-clase/{id} con un nombre válido y otro inválido.

Verifica en PostgreSQL: revisa las tablas socio y reserva para confirmar que reservas_activas coincide siempre con la cantidad de reservas cuyo campo asistio es false.

Desafío opcional: beneficios del gimnasio (@ManyToMany)

Amplía el proyecto con una relación muchos a muchos similar a RoleEntity en clase:

  1. Crea BeneficioEntity (tabla beneficio) con id: UUID, nombre único (ej. SAUNA, ESTACIONAMIENTO, NUTRICIONISTA) y descripcion.
  2. Relaciona BeneficioEntity y SocioEntity con @ManyToMany mediante la tabla intermedia socio_beneficio (beneficio_id, socio_id).
  3. Implementa POST /api/v1/beneficio/save, POST /api/v1/socio/{idSocio}/beneficios/{idBeneficio} (evitando asignaciones duplicadas) y GET /api/v1/socio/{idSocio}/beneficios.
