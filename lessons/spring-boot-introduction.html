Una conversación entre programas

Cómo se comunican el navegador y la aplicación

Como en una conversación con reglas compartidas, un programa envía una solicitud y el otro devuelve una respuesta. Ese conjunto de reglas se llama protocolo.

Cliente
El navegador solicita A-17
⇄
Servidor

En la web, un protocolo muy usado para esta conversación es HTTP (Protocolo de Transferencia de Hipertexto).

localhost significa este mismo equipo. 8080 es el puerto: una entrada numerada para la aplicación; Spring Boot suele usarlo por defecto.

/pedidos/A-17

La ruta, o path, identifica lo que se solicita. No es la URL completa.

Dos intenciones distintas

GET consulta; POST envía algo nuevo

GET

Recuperar información. Ejemplo: consultar A-17.

/pedidos/A-17
POST

Enviar datos para crear o procesar algo. Ejemplo: enviar los datos de un nuevo pedido.

/pedidos
El método expresa qué operación solicita el cliente; no es el resultado de la solicitud.
Otras operaciones posibles

Actualizar o retirar un pedido también requiere una solicitud

PUT

Solicitar reemplazar la representación completa de A-17.

PATCH

Solicitar un cambio parcial, por ejemplo cambiar su estado.

DELETE

Solicitar retirar A-17.

Que el cliente lo solicite no garantiza que el servidor lo permita ni que lo guarde: depende de cómo se implemente y de sus reglas. Aquí no estamos borrando A-17.
La respuesta informa qué ocurrió

El código de estado resume el resultado HTTP

2xx · solicitud atendida

200 OK consulta respondida.

201 Created se creó algo.

204 No Content se atendió sin contenido de respuesta.

4xx · problema de solicitud

400 Bad Request solicitud inválida.

404 Not Found no se encontró la ruta o el recurso solicitado.

5xx · problema al atender

500 Internal Server Error error inesperado del servidor.

El método dice qué se pide (GET, POST…). El estado comunica cómo terminó.

Una consulta puede terminar en 200 o en 404

Dos causas diferentes para 404

Ruta no implementada: esta aplicación no reconoce /rutas/otra.

Recurso no encontrado: en una aplicación conectada a datos, no existe el pedido solicitado.

En nuestra implementación fija de más adelante, A-17 responde; si la ruta no está mapeada, no hay controlador que la atienda. Comprobar si un ID existe requiere lógica o datos; no aparece automáticamente.

Qué devuelve la API

La respuesta describe el pedido A-17

La API trata el pedido como un recurso: algo identificable sobre lo que se puede consultar.

Una representación es una forma acordada de expresar sus datos. JSON es un formato de texto legible para agrupar valores con nombres.

JSON es un formato de intercambio, no una base de datos.
Organizar operaciones de una API

Mismo pedido · otro tipo de contrato

REST identifica recursos; SOAP define mensajes XML

Supongamos que otra aplicación también necesita consultar A-17. Puede acordar una interfaz diferente para obtener los mismos datos.

API de pedidos diseñada con REST

GET /pedidos/A-17

El recurso y el método HTTP indican la consulta. En este curso la respuesta usa 200 + JSON.

Servicio que usa SOAP

Operación: ConsultarPedido
Dato enviado: ID A-17

La solicitud y la respuesta usan mensajes XML con un sobre SOAP. Un documento WSDL suele describir las operaciones y los mensajes disponibles.

SOAP es un protocolo de mensajería, no otro nombre para REST ni para JSON. Puede transportarse por HTTP, pero su mensaje tiene reglas propias.
Otras formas de ofrecer una API

También podemos pedir campos o llamar a un método remoto

GraphQL · elegir los campos

Un cliente puede pedir solo el estado y el total de A-17, si la API ofrece estos campos:

{ pedido(id: "A-17") {
    estado
    totalSoles
  }
}

GraphQL es un lenguaje de consultas y una forma de ejecutarlas; no reemplaza a HTTP.

gRPC · llamar a otro servicio
Método remoto
ConsultarPedido
entrada: ID A-17 → salida: datos de A-17

gRPC permite llamadas a métodos remotos entre servicios. Suele usar HTTP/2 y Protocol Buffers, un formato binario con un esquema de mensajes.

Son alternativas según la necesidad: REST encaja con recursos web; SOAP con contratos de mensajería estandarizados; GraphQL cuando el cliente elige campos; gRPC para llamadas tipadas entre servicios. Para nuestro ejemplo sencillo seguiremos con REST.

Implementar la primera operación

El controlador atiende GET y devuelve datos

Clase completa · PedidoController.java
package ejemplo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

record PedidoRespuesta(
    String id, String estado, int totalSoles) {}

@RestController
public class PedidoController {
  @GetMapping("/pedidos/A-17")
  public PedidoRespuesta consultarA17() {
    return new PedidoRespuesta(
        "A-17", "EN_PREPARACION", 36);
  }
}

@RestController indica que los resultados de sus métodos se devuelven como datos web.

@GetMapping relaciona esa ruta con una consulta GET. El método devuelve un objeto Java PedidoRespuesta.

Con Spring Web y su conversor JSON habitual, los datos del objeto se convierten en texto JSON. Esta conversión se llama serialización; no devolvemos una cadena que solo parezca JSON.

Ejemplo fijo en memoria: no busca en una base de datos ni ofrece otros ID.

Alcance del ejemplo

Esta primera respuesta todavía es fija

Lo que sí hace

Responde la ruta exacta /pedidos/A-17 con un objeto y su representación JSON.

Lo que aún no hace

No lee la base de datos tienda, no encuentra otros IDs, no almacena cambios ni implementa CRUD completo.

Para consultar pedidos guardados, la aplicación tendría que conectarse a datos y pedir el registro correspondiente. Esa será una pieza posterior.

Organizar y construir un proyecto Java

Maven evita preparar cada proyecto a mano

Una aplicación necesita bibliotecas —por ejemplo, Spring Web y el driver PostgreSQL— y una forma consistente de compilar, probar y empaquetar el código.

→

Comandos de construcción

Qué problema resuelve

Sin un gestor, el equipo tendría que buscar archivos JAR, agregarlos manualmente y coordinar sus versiones y dependencias.

Ventajas

Un archivo pom.xml compartido facilita repetir la configuración, descargar dependencias transitivas y usar tareas estándar en el equipo o en integración continua.

Maven es una herramienta de construcción y gestión de dependencias, no una biblioteca Java ni una base de datos. Requiere acceso a un repositorio de dependencias al descargarlas por primera vez.
Maven · pom.xml

El proyecto declara por separado qué piezas necesita

Fragmento de pom.xml · dependencias
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>
</dependency>

Spring Data JPA aporta integración para trabajar con datos mediante repositorios.

PostgreSQL JDBC es el driver que permite a Java hablar con PostgreSQL; Maven lo descarga como dependencia.

El driver es independiente de Lombok. No agregues ambos esperando que uno instale al otro.
application.properties

Spring Boot usa la URL y las credenciales para conectar

src/main/resources/application.properties
spring.datasource.url=jdbc:postgresql://localhost:5432/tienda
spring.datasource.username=postgres
spring.datasource.password=CAMBIAR_ESTA_CLAVE
spring.jpa.hibernate.ddl-auto=update
Qué ocurre al iniciar

Spring Boot lee la configuración, encuentra el driver PostgreSQL y prepara un DataSource para abrir conexiones.

localhost:5432 señala PostgreSQL en este equipo; tienda es la base de datos. El servidor PostgreSQL debe estar instalado y en ejecución.

ddl-auto=update es una opción didáctica para desarrollo, no una recomendación universal para producción. No guardes contraseñas reales en el repositorio.
