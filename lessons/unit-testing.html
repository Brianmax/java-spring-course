La idea antes de la sintaxis

Una prueba unitaria convierte criterios de aceptación en código ejecutable

Cuando un cambio nuevo rompe un comportamiento que antes funcionaba, ocurre una regresión. Una prueba unitaria verifica una sola unidad de comportamiento de forma aislada, automática y rápida.

Rápida

Corre en milisegundos; se ejecuta tras cada cambio.

Aislada

No depende de BD, red ni del orden de otras pruebas.

Repetible

Mismo resultado en tu PC, la de Diego y en integración continua (CI).

Autoverificable

Responde pasa o falla sin leer logs a mano.

Conecta explícitamente el término regresión con el incidente de Diego en la diapositiva anterior. Aún no mostramos anotaciones de JUnit: primero el concepto mental claro.

Toda prueba clara sigue tres pasos: Arrange, Act, Assert

Antes de memorizar anotaciones, ordena siempre cada prueba en tres bloques visibles sobre el pedido ORD-205:

1 · Arrange (Preparar) Crear escenario limpio

Instancia CalculadoraDescuento y cupón DESC20 (20%, mín. 100, tope 50).

Subtotal de ORD-205 = S/ 200

ejecuta
2 · Act (Actuar) Una sola acción

Llama a calcularDescuento(200, desc20) y guarda el valor devuelto.

Resultado real = descuento

compara
3 · Assert (Comprobar) Verificar promesa

Comprueba que el resultado real coincide con el valor esperado.

Nombre orientado a comportamiento: nombra cada prueba por el escenario y el resultado esperado (por ejemplo, debeAplicar20PorCientoCuandoSuperaMinimo), no como test1().
AAA también aparece en libros como Given / When / Then. Lo esencial es no mezclar cinco acciones distintas en un mismo método de prueba.
Bloque 1 · biblioteca de pruebas JUnit Jupiter

De AAA a código ejecutable con @Test y assertEquals

src/test/java/.../CalculadoraDescuentoTest.java · JUnit Jupiter
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class CalculadoraDescuentoTest {

  @Test
  @DisplayName("ORD-205: aplica 20% cuando el subtotal supera el mínimo")
  void debeAplicar20PorCientoCuandoSuperaMinimo() {
    // Arrange
    var calculadora = new CalculadoraDescuento();
    var desc20 = new Cupon("DESC20", 20, 100, 50, true); // 20%, mín 100, tope 50, activo

    // Act
    int descuento = calculadora.calcularDescuento(200, desc20);

    // Assert · primero esperado, segundo real
    assertEquals(40, descuento);
  }
}
Lenguaje vs. Biblioteca

JUnit Jupiter (org.junit.jupiter.api) es una biblioteca de pruebas en Maven, no parte del JDK ni de Spring Boot.

Orden en assertEquals

Escribe assertEquals(esperado, real). Si falla, JUnit dirá «expected: 40 but was: 0»; invertirlos confunde el diagnóstico.

Ubicación y ejecución

Vive en src/test/java reflejando el paquete de src/main/java. Se ejecuta desde el IDE o con mvn test.

Aclara que en Spring Boot 4 (spring-introduccion/pom.xml) JUnit Jupiter viene listo mediante los starters de test y mantiene exactamente el mismo paquete org.junit.jupiter.api que JUnit 5.
Bloque 2 · tope máximo y reglas de rechazo

Verificar tope (ORD-206) y excepciones (ORD-208)

Fragmento de CalculadoraDescuentoTest.java · tope y excepción
@Test
void debeLimitarDescuentoAlTopeDe50EnOrd206() {
  var calculadora = new CalculadoraDescuento();
  var desc20 = new Cupon("DESC20", 20, 100, 50, true);

  assertEquals(50, calculadora.calcularDescuento(400, desc20));
}

@Test
void debeLanzarExcepcionSiSubtotalEsMenorAlMinimoEnOrd208() {
  var calculadora = new CalculadoraDescuento();
  var desc20 = new Cupon("DESC20", 20, 100, 50, true);

  var error = assertThrows(MontoMinimoNoAlcanzadoException.class,
      () -> calculadora.calcularDescuento(80, desc20));
  assertAll(
      () -> assertEquals(100, error.minimoRequerido()),
      () -> assertEquals(80, error.subtotalRecibido())
  );
}
¿Por qué lleva lambda () -> ...?

Si llamaras al método fuera de la lambda, la excepción explotaría antes de entrar a assertThrows. La lambda entrega la acción para que JUnit la ejecute y capture el error esperado.

Otras aserciones frecuentes
  • assertAll(...): evalúa todas las comprobaciones y reporta cada fallo junto.
  • assertTrue / assertFalse: condiciones booleanas claras.
  • assertNotNull / assertDoesNotThrow: presencia y ejecución sin error.
Señala que assertThrows devuelve la instancia de la excepción capturada, útil cuando también importa comprobar un código de error o un dato clave del mensaje sin atarse a una redacción rígida.

Bloque 2 · pruebas independientes del orden

JUnit aísla cada prueba con @BeforeEach

Por defecto, JUnit crea una instancia nueva de la clase de prueba por cada método @Test y ejecuta @BeforeEach antes de cada caso para evitar contaminación entre pruebas.

nueva instancia
Instancia #2 @BeforeEach

Caso 2 @Test ORD-207

Pasa en cualquier orden

Extraer la preparación repetida sin compartir estado · CalculadoraDescuentoTest
CalculadoraDescuento calculadora;
Cupon desc20;

@BeforeEach
void setUp() {
  calculadora = new CalculadoraDescuento();
  desc20 = new Cupon("DESC20", 20, 100, 50, true);
}
Error común · estado mutable compartido

Un static List o un cupón mutable modificado por el Test A hace que el Test B falle al cambiar el orden.

Otros ganchos de ciclo

@AfterEach limpia tras cada prueba. @BeforeAll / @AfterAll corren una sola vez por clase y deben ser static en el ciclo por defecto.

Enfatiza que ninguna prueba debe depender de que otra corra antes. Si necesitas un orden fijo entre pruebas unitarias, hay estado compartido oculto que conviene eliminar.

Bloque 3 · conceptos antes de Mockito

Tres tipos de dobles de prueba: Stub, Fake y Mock

Para aislar las fronteras externas de AplicarCuponService, reemplazamos sus contratos por dobles de prueba (objetos de sustitución). Cada tipo cumple un papel distinto:

1 · Stub

Controla entradas

Devuelve respuestas fijas preconfiguradas para guiar el camino de la prueba.

Ejemplo: buscarPorId("ORD-205") siempre devuelve el pedido de S/ 200; "ORD-999" devuelve Optional.empty().

2 · Fake

Implementación en memoria

Funciona de verdad con una versión ligera (p. ej. un HashMap), sin BD real.

Ejemplo: PedidoRepositoryEnMemoria guarda y luego permite consultar el estado actualizado (como vimos en Hexagonal).

3 · Mock

Verifica interacciones

Además de devolver respuestas preparadas, registra si el servicio invocó un método y con qué datos.

Ejemplo: comprobar que notificador.avisarDescuento("ORD-205", 40) se llamó una vez (o cero si falló).

Prerrequisito clave: los tres dobles funcionan porque AplicarCuponService recibe sus dependencias como interfaces por constructor (diseño POO/DIP, no magia de Spring).
Aclara que en el día a día muchos llaman "mock" a todo, pero distinguir Stub (entradas), Fake (estado ligero en memoria) y Mock (verificar llamadas) evita pruebas confusas.
Bloque 3 · biblioteca Mockito con JUnit Jupiter

Preparar dobles sin clases manuales con Mockito

src/test/java/.../AplicarCuponServiceTest.java · configuración inicial
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class AplicarCuponServiceTest {

  @Mock PedidoRepository pedidoRepo;
  @Mock CuponRepository cuponRepo;
  @Mock NotificadorCliente notificador;

  AplicarCuponService service;

  @BeforeEach
  void setUp() {
    service = new AplicarCuponService(
        pedidoRepo, cuponRepo, notificador, new CalculadoraDescuento());
  }
}
JUnit + Mockito (sin Spring)

@ExtendWith(MockitoExtension.class) es una extensión de JUnit provista por Mockito: inicializa cada @Mock antes de cada prueba sin arrancar Spring.

CalculadoraDescuento real

Solo mockeamos las tres fronteras externas; la calculadora entra como instancia real para probar el cálculo de verdad.

Constructor explícito vs. @InjectMocks

@InjectMocks ahorra líneas, pero llamar a new AplicarCuponService(...) en @BeforeEach detecta en compilación cualquier cambio del constructor y deja mezclar mocks con objetos reales.

Señala el beneficio práctico de usar new AplicarCuponService(...) en @BeforeEach: es explícito, claro para principiantes y permite pasar new CalculadoraDescuento() sin trucos de @Spy.
Bloque 3 · programar respuestas del colaborador

Controlar entradas con when(...).thenReturn(...) y thenThrow(...)

Casos ORD-205 (éxito) y ORD-999 (ausente) en AplicarCuponServiceTest
@Test
void debeAplicarDesc20YDevolverTotal160ParaOrd205() {
  var pedido = new Pedido("ORD-205", 200);
  var desc20 = new Cupon("DESC20", 20, 100, 50, true);
  when(pedidoRepo.buscarPorId("ORD-205")).thenReturn(Optional.of(pedido));
  when(cuponRepo.buscarPorCodigo("DESC20")).thenReturn(Optional.of(desc20));

  ResultadoDescuento r = service.aplicar("ORD-205", "DESC20");

  assertEquals(160, r.totalFinal());
}

@Test
void debeFallarSiElPedidoOrd999NoExiste() {
  when(pedidoRepo.buscarPorId("ORD-999")).thenReturn(Optional.empty());

  assertThrows(PedidoNoEncontradoException.class,
      () -> service.aplicar("ORD-999", "DESC20"));
}
Qué hace cada when(...)

En Arrange le dices al mock qué devolver cuando el servicio le pregunte por "ORD-205" o "ORD-999". Si no programas un método, Mockito devuelve valores por defecto (Optional.empty(), 0, null).

Simular un fallo técnico con thenThrow
when(pedidoRepo.buscarPorId("ORD-205"))
    .thenThrow(new ErrorPersistenciaException("BD caída"));

Permite probar manejo de errores técnicos sin apagar una base de datos real.

Haz notar que MockitoExtension en modo estricto (por defecto) también avisa con UnnecessaryStubbingException si declaras un when(...) que el servicio nunca llamó: ayuda a mantener pruebas limpias.
Bloque 3 · efectos observables y ausencia de llamadas

Comprobar guardado y aviso con verify, never() y ArgumentCaptor

Verificar qué se guardó y garantizar silencio cuando falla VENCIDO10
// En el caso exitoso ORD-205 + DESC20:
ArgumentCaptor<Pedido> captor = ArgumentCaptor.forClass(Pedido.class);
verify(pedidoRepo).guardar(captor.capture());
assertEquals(160, captor.getValue().totalFinal());
verify(notificador).avisarDescuento("ORD-205", 40);

// En el caso fallido ORD-205 + VENCIDO10 (cupón inactivo):
when(pedidoRepo.buscarPorId("ORD-205")).thenReturn(Optional.of(pedido));
when(cuponRepo.buscarPorCodigo("VENCIDO10"))
    .thenReturn(Optional.of(new Cupon("VENCIDO10", 10, 100, 50, false)));

assertThrows(CuponInvalidoException.class,
    () -> service.aplicar("ORD-205", "VENCIDO10"));
verify(pedidoRepo, never()).guardar(any());
verifyNoInteractions(notificador);
Qué atrapa ArgumentCaptor

No basta comprobar que guardar(...) se llamó: con el captor verificamos que el objeto Pedido enviado a la BD lleva totalFinal == 160.

Regla de oro de los matchers (comodines)

Si usas un matcher (comodín de argumento como any() o anyInt()) en una llamada de Mockito, todos los argumentos deben ser matchers:

✗ avisarDescuento("ORD-205", anyInt())
✓ avisarDescuento(eq("ORD-205"), anyInt())

Resalta la importancia de verifyNoInteractions(notificador) cuando el cupón está vencido: evita un bug muy real en producción donde se envía correo de descuento a pesar de que la operación falló.
Bloque 4 · error común con Mockito

Sobre-mockear prueba el mock en lugar de tu lógica

Un riesgo frecuente al aprender Mockito es mockear demasiado y verificar cada paso interno en lugar de comprobar el resultado observable.

Anti-patrón · prueba frágil y engañosa
@Mock CalculadoraDescuento calcMock; // ¡regla pura!
...
when(calcMock.calcularDescuento(200, desc20))
    .thenReturn(40);
var r = service.aplicar("ORD-205", "DESC20");
assertEquals(160, r.totalFinal());
verify(calcMock).calcularDescuento(200, desc20);

Si la calculadora real tiene un bug, esta prueba sigue pasando porque solo devolvió tu propio thenReturn(40). Además, cualquier refactor interno rompe el verify.

Enfoque sólido · mockea solo fronteras externas
  • Usa objetos reales para entidades, DTOs y reglas puras (Pedido, Cupon, CalculadoraDescuento).
  • Sustituye solo fronteras: base de datos, HTTP externo, mensajería, reloj o correo.
  • Verifica comportamiento observable: valor retornado, excepción lanzada y efectos externos relevantes (guardar, avisarDescuento).
Regla práctica: una buena prueba unitaria te deja refactorizar cómo está escrito el servicio por dentro sin romperse, mientras el comportamiento externo siga igual.
Pregunta a la clase: si mañana decides mover el cálculo de descuento dentro de un método Pedido.aplicarCupon(cupon) manteniendo el resultado S/ 160, ¿qué prueba sobrevive? La del enfoque sólido.
Bloque 4 · criterio de diseño

Fake en memoria frente a Mockito: cuándo conviene cada uno

En Arquitectura Hexagonal probamos servicios con un fake en memoria (Map); hoy vimos Mockito. No compiten como «bueno vs. malo»: cada herramienta resuelve mejor distintos casos.

CriterioFake en memoria (Map / List)Mock con Mockito (@Mock)
Trabajo inicial Requiere escribir y mantener una clase en memoria para el puerto. Inmediato: declaras @Mock y programas solo el caso actual.
Flujos con estado Excelente cuando una prueba guarda y luego consulta el mismo estado. Más verboso si debes encadenar varios when(...) sucesivos.
Simular errores raros Exige agregar banderas al fake para forzar fallos de red o BD. Muy ágil con una sola línea: when(...).thenThrow(...).
Acoplamiento al refactor Menor: compruebas el estado resultante en el mapa o lista. Mayor si abusas de verify(...) sobre llamadas internas.
Criterio equilibrado: un fake en memoria destaca en repositorios reutilizados por muchas pruebas; Mockito brilla para simular fallos puntuales y verificar salidas hacia clientes externos (correo, SMS, pasarelas).
Conecta explícitamente con la lección anterior de Arquitectura Hexagonal para que el alumno no perciba contradicción entre ambos enfoques.

Bloque 4 · alcance honesto en Spring Boot

Lo que las pruebas unitarias cubren y lo que exige integración

Mockito y los fakes confirman tus reglas y coordinación en milisegundos, pero no demuestran que una consulta SQL, un mapeo JPA o una ruta HTTP funcionen de verdad.

Nivel de pruebaHerramienta típicaQué valida realmenteVelocidad
Unitaria JUnit Jupiter + Mockito o Fakes (sin Spring) Reglas de CalculadoraDescuento, bordes, excepciones y orquestación de AplicarCuponService. Milisegundos
Slice web (capa HTTP) @WebMvcTest + MockMvc Ruta POST /pedidos/{id}/aplicar-cupon, JSON de entrada/salida y códigos 200 / 404 / 409. Rápida (~1–2 s)
Slice de datos (capa JPA) @DataJpaTest + BD de prueba Consultas SQL/JPQL, anotaciones @Entity y restricciones de columnas en repositorios. Media
Integración completa @SpringBootTest Cableado real de beans, filtros, configuración y flujo extremo a extremo. Más lenta
Complementarias, no rivales: muchas pruebas unitarias rápidas protegen la lógica diaria; un grupo enfocado de pruebas de integración valida las fronteras reales. En spring-introduccion/pom.xml, los starters *-test ya incluyen JUnit Jupiter y Mockito.
Recuerda al grupo no levantar @SpringBootTest para probar un simple cálculo o un servicio que puede correr en Java puro con @ExtendWith(MockitoExtension.class).
Resumen · volver a TICKET-14 y TICKET-28

Cuatro hábitos para que ningún ticket rompa el trabajo anterior

1 · Estructura AAA

Preparar, actuar y comprobar con nombres claros y pruebas aisladas en @BeforeEach.

2 · Bordes y errores

Proteger límites exactos (ORD-207 S/ 100) con @ParameterizedTest y assertThrows.

3 · Aislar fronteras

Sustituir BD y correo con Fakes o Mockito; nunca mockear reglas puras como CalculadoraDescuento.

4 · Evidencia real

No fiarse solo del % de cobertura y complementar con integración para HTTP y SQL.

Comprueba 1: ¿Por qué el cambio de Diego en TICKET-28 rompió ORD-207?

Cambió >= 100 a > 100 y solo verificó manualmente sus casos (200 y 80).

Comprueba 2: ¿Por qué CalculadoraDescuento no lleva @Mock?

Es lógica pura interna; mockearla ocultaría errores reales en el cálculo.

Comprueba 3: ¿Qué error NO atrapa AplicarCuponServiceTest con mocks?

Una query SQL mal escrita, un mapeo @Entity roto o una ruta HTTP incorrecta.

Contratos PedidoRepository, CuponRepository, NotificadorCliente y la clase pura CalculadoraDescuento. Casos: ORD-205 (200), ORD-206 (400), ORD-207 (100), ORD-208 (80), ORD-999 (ausente) y VENCIDO10 (inactivo).

Resultado esperado

Batería verde que valide: montos válidos y bordes (100 / 200 / 250 / 400) con @ParameterizedTest, rechazos (80 / 99, ORD-999, VENCIDO10) con assertThrows, guardado del total actualizado y cero notificaciones cuando falla.

Restricciones

Sin @SpringBootTest, sin PostgreSQL ni envío de correo real, sin mockear CalculadoraDescuento y sin depender del orden de ejecución entre métodos @Test.

Desafío opcional: usa ArgumentCaptor<Pedido> para verificar el total exacto enviado a guardar(...) y luego crea una variante con un Fake en memoria para PedidoRepository comparando legibilidad y esfuerzo.
Para verificar la efectividad de su suite, reta a los alumnos a introducir el cambio de Diego (> 100 en vez de >= 100) y confirmar que la prueba de ORD-207 se pone en rojo de inmediato.
