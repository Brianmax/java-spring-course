Básico · Programación orientada a objetos

POO es un paradigma: organiza el programa con objetos

Un paradigma es una forma de diseñar y organizar un programa. En POO, modelamos objetos que reúnen datos (estado) y acciones relacionadas (comportamiento).

Estado: valores actuales, como cantidad 2 y precio $5.

Comportamiento: acciones del objeto, como calcular el total.

Quien consulta pide el total al pedido; ya no reúne precio y cantidad en cada llamada. Agrupar organiza los datos; las reglas aún deben programarse.

Fundamentos de la POO

La POO organiza el programa alrededor de objetos: reúnen estado, comportamiento y relaciones.

Piezas de una clase

Clase: descripción para crear objetos.

Objeto: ejemplar concreto con identidad.

Atributos / estado: datos que conserva el objeto.

Métodos / comportamiento: acciones o consultas.

Constructor: prepara el objeto al crearlo.

Principios

Abstracción: mostrar lo necesario para usar algo.

Encapsulamiento: proteger estado y aplicar reglas al cambiarlo.

Herencia: especializar una clase reutilizando otra.

Polimorfismo: misma operación, respuesta propia del objeto.

Relaciones y contratos

Asociación: objetos que se conocen o colaboran.

Agregación: una parte que puede vivir por separado.

Composición: una parte pertenece a un todo y depende de él.

Interfaz / contrato: capacidades que una clase se compromete a ofrecer.

Básico · Unidad 2 · Declarar una clase

Una clase reúne campos y métodos

Declaración de la clase Pedido
class Pedido {
    String producto = "cuaderno";
    int unidades = 2;
    int precioDolares = 5;
    int calcularTotal() {
        return unidades * precioDolares;
    }
    void agregarUnidad() { unidades++; }
}

class Pedido nombra la clase; las llaves delimitan su cuerpo. Los tres campos guardan el estado propio de cada objeto; calcularTotal() usa dos de ellos sin recibir parámetros.

Fragmento dentro de main · crear dos objetos
Pedido primero = new Pedido();
Pedido segundo = new Pedido();
segundo.producto = "carpeta";
segundo.unidades = 1;
segundo.precioDolares = 12;
int total = primero.calcularTotal(); // $10
primero.agregarUnidad(); // 2 → 3

int calcularTotal() devuelve 2 × $5 = $10 antes del cambio. void agregarUnidad() modifica 2 → 3 sin devolver un valor; después el total de A-17 sería $15.

new Pedido() inicia cada objeto con cuaderno, 2 unidades y $5; el segundo se ajusta a carpeta, 1 unidad y $12. A-17 (primero) termina en 3; B-18 (segundo) sigue en 1.

Básico · Unidad 2 · Referencias

Copiar la referencia no copia el objeto

Fragmento dentro de main · continúa el anterior
Pedido alias = primero;
alias.agregarUnidad();

primero y alias alcanzan el mismo A-17: 3 → 4 cuadernos a $5. B-18 conserva 1 carpeta a $12.

Copiar primero a alias copia la referencia, no los campos de A-17. Ambos nombres llegan al mismo pedido.

null no apunta a ningún objeto; llamar allí un método lanza NullPointerException.

Básico · Unidad 2 · Referencias

Al crear un objeto con new, la variable recibe una referencia

La variable no contiene el objeto: guarda una referencia (una flecha) hacia él. Por eso primero.producto, primero.unidades y primero.precioDolares leen sus campos. Cada vez que se evalúa new se crea un objeto nuevo.

Simplificación del dibujo: aquí separamos la variable y el objeto. En la implementación típica el objeto se reserva aparte, en una zona de memoria llamada montón (heap); la regla del lenguaje es solo que la variable guarda una referencia.

Básico · Unidad 4 · Estado protegido

Encapsular: cambiar el stock mediante operaciones

class Inventario {
    private int stock = 5;
    public boolean retirar(int unidades) {
        if (unidades <= 0 || unidades > stock) return false;
        stock -= unidades;
        return true;
    }
    public int consultarStock() { return stock; }
}
Regla y resultados · cada intento parte de 5

retirar(2) → true · stock queda en 3.

retirar(8) → false · stock sigue en 5.

Encapsular protege el estado interno y permite cambiarlo mediante operaciones que aplican reglas. stock es privado; retirar y consultarStock son públicos. Un getter o setter puede ser válido si encaja con las reglas del modelo.

Básico · Unidad 4 · Visibilidad

Quién puede acceder a cada miembro

ModificadorAlcance
publicDesde cualquier clase que pueda ver ese tipo.
privateOculto para otras clases independientes; se usa dentro de la clase declaradora.
sin modificadorClases del mismo paquete, un grupo de clases relacionadas.
protectedMismo paquete; también subclases fuera de él, con restricciones sobre el tipo de referencia usado.

Un getter permite consultar cuando conviene; un setter no es obligatorio. protected no significa “todo objeto hijo puede acceder a todo”.

Básico · Unidad 5 · Inmutabilidad

Inmutable: el código del producto permanece igual

Un objeto es inmutable si sus datos observables no cambian después de crearlo. El producto CU-10 conserva su código.

Al crear Producto

Código CU-10

El constructor guarda el String en un campo privado final.

Después

Sigue siendo CU-10

No hay operación para cambiarlo; para representar CU-99, crea otro Producto.

Aquí funciona porque String también es inmutable. Si un campo guarda un objeto mutable, final solo fija la referencia: podrían necesitarse copias al recibirlo o devolverlo.

Básico · Unidad 6 · Herencia

Herencia: reutilizar y especializar una clase

Declaraciones de clases
class Entrega {
    public int diasEstimados() { return 5; }
}

class EntregaExpress extends Entrega {
    // Hereda diasEstimados()
}
Fragmento dentro de main
EntregaExpress express =
    new EntregaExpress();
express.diasEstimados(); // 5

EntregaExpress hereda diasEstimados() de Entrega: puede llamarlo sin escribirlo otra vez.

extends declara “es una”. Los constructores no se heredan; después especializamos el plazo con @Override.

Hereda solo si la subclase también cumple las promesas de la clase base; no uses herencia únicamente para copiar código.

Básico · Unidad 6 · Sobrescritura

Sobrescribir una operación con @Override

class Entrega {
    public int diasEstimados() { return 5; }
}
class EntregaExpress extends Entrega {
    @Override
    public int diasEstimados() { return 1; }
}

Misma petición

Objeto Entrega → 5 días

Objeto EntregaExpress → 1 día

La firma coincide; @Override pide al compilador revisar ese hecho.

Los atributos heredados no se reemplazan dinámicamente como los métodos de instancia.

Básico · Unidad 6 · Inicialización de subclase

super reutiliza la parte heredada

class Entrega {
    private final String destino;
    Entrega(String destino) { this.destino = destino; }
}
class EntregaExpress extends Entrega {
    EntregaExpress(String destino) {
        super(destino);
    }
}

super(destino) inicializa primero la parte base. super.metodo() puede llamar su implementación.

Los constructores no se heredan. final puede impedir extender una clase o sobrescribir un método.

No extiendas solo para reutilizar código: ¿una entrega programada cumple el contrato general?

Básico · Unidad 7 · Implementación

Una clase abstracta combina contrato y código

abstract class Entrega {
    public abstract int diasEstimados();
    public String resumen() {
        return "Plazo (días): " + diasEstimados();
    }
}
class EntregaExpress extends Entrega {
    public int diasEstimados() { return 1; }
}

new EntregaExpress().resumen()

La clase abstracta puede tener estado y constructores. Su método abstracto no tiene cuerpo.

No puedes crear new Entrega(); falta una implementación concreta.

Agrega otra variante y conserva el método resumen.

Básico · Unidad 8 · Ejecución

Polimorfismo: mismo pedido, distinta respuesta

Polimorfismo: tipos relacionados responden a la misma llamada con su propia implementación. Entrega determina las operaciones disponibles; la clase real EntregaExpress determina cuál se ejecuta: diasEstimados() devuelve 1 día.

Usa la operación común sin preguntar la clase concreta.

Básico · Unidad 8 · Comparación

Sobrecarga y sobrescritura se deciden distinto

Sobrecarga · fragmento de clase

public int totalConEnvio(int totalDolares) {
    return totalDolares + 5;
}
public int totalConEnvio(
        int totalDolares, boolean express) {
    return express ? totalDolares + 9
                   : totalConEnvio(totalDolares);
}

Volvemos al A-17 original, 2 cuadernos a $5 = $10, antes de los cambios de referencias de la unidad 2: totalConEnvio(10) → $15; totalConEnvio(10, true) → $19. Se distinguen por sus parámetros.

Sobrescritura · EntregaExpress

@Override
public int diasEstimados() {
    return 1;
}

Firma heredada; la clase real elige el cuerpo al ejecutar.

No se sobrecarga cambiando solo el retorno. Campos y métodos static tampoco tienen despacho dinámico.

Intermedio · Unidad 9 · contratos y jerarquías

Interfaz o clase abstracta

Interfaz

Define capacidades que clases distintas pueden ofrecer.

Una clase puede implementar varias interfaces.

Clase abstracta

Puede reunir estado y código compartido dentro de una jerarquía.

Intermedio · Unidad 9 · ampliar el contrato

Intermedio · Unidad 12 · declarar y lanzar

throw lanza; throws declara

Inventario · valida antes de cambiar el stock
class Inventario {
    private int stock = 5;
    void retirar(int n) {
        if (n <= 0)
            throw new IllegalArgumentException();
        if (n > stock)
            throw new StockInsuficienteException();
        stock -= n;
    }
    int consultarStock() { return stock; }
}
Definición de la excepción propia
class StockInsuficienteException
        extends RuntimeException {
    StockInsuficienteException() {
        super("Stock insuficiente");
    }
}

throw lanza ahora; throws declara en la firma, por ejemplo void leer() throws java.io.IOException.

Cada intento parte de 5: retirar(2) deja consultarStock() = 3; retirar(8) lanza y conserva 5. La excepción de stock es RuntimeException: no exige throws.

Intermedio · Unidad 12 · tipos de excepción

Elegir el contrato de error

Dentro de main · Inventario de la diapositiva anterior
Inventario inventario = new Inventario();
try {
    inventario.retirar(8);
} catch (StockInsuficienteException error) {
    System.out.println(error.getMessage());
} finally {
    System.out.println("Intento terminado");
}

Verificada

Una subclase de Exception que no sea RuntimeException: se captura o se declara con throws.

No verificada

RuntimeException y sus subclases no obligan a capturar ni declarar.

El catch informa el rechazo; quedan 5 unidades. finally se ejecuta al salir del bloque, salvo terminaciones abruptas de la JVM.
