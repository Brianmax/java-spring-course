Arquitectura hexagonal en Spring Boot

Ya construimos APIs REST con Spring Boot, JPA y PostgreSQL. El reto real llega cuando el repositorio debe cambiar tecnologías o sumar nuevos canales e integraciones.

Tomaremos como caso base un endpoint con reglas de negocio reales: PATCH /pedidos/{id}/cancelar.

Objetivo: aislar las reglas de negocio para cambiar BD, pasarelas de pago, mensajería o canales de entrada sin reescribir el núcleo.
Reglas del endpoint · PATCH /pedidos/{id}/cancelar
ORD-101 · S/ 120 · EN_PREPARACION 200 OK → CANCELADO ORD-102 · S/ 85 · ENTREGADO 409 Conflict · rechazado ORD-999 · ID inexistente 404 Not Found

409 Conflict indica que la operación choca con el estado actual del recurso.

A esta altura el grupo ya sabe construir APIs REST en Spring Boot con JPA. Arrancamos directo en un escenario backend realista con reglas de negocio y el problema de evolucionar el repositorio.
Punto de partida · lo que ya construimos

La distribución en capas de Spring Boot ya resuelve esto

Con nuestra estructura actual (controller, service, repository, entity, dto), el endpoint PATCH /pedidos/{id}/cancelar funciona de extremo a extremo.

Entrada HTTP PATCH /pedidos/{id}/cancelar
controller · dto PedidoController usa PedidoResponse
service PedidoService valida regla y guarda
repository · entity PedidoRepository JPA → PostgreSQL
controller / dto

Recibe la ruta HTTP y serializa PedidoResponse.

service

Aplica la regla de cancelación sobre ORD-101 / ORD-102.

repository / entity

JpaRepository lee y actualiza PedidoEntity en PostgreSQL.

Esta arquitectura en capas funciona bien para entregar la primera versión. El problema no está en cómo corre hoy, sino en qué pasa al evolucionar el repositorio.
Refuerza que la arquitectura en capas no está «mal»: es la misma estructura de spring-introduccion y entrega resultados válidos. Ahora inspeccionaremos el acoplamiento interno.
Mirar dentro del servicio actual

La regla de negocio convive con JPA, Spring y DTOs

Fragmento Java · service/PedidoService.java (en capas)
@Service
public class PedidoService {
  private final PedidoRepository repo; // extiende JpaRepository

  public Optional<PedidoResponse> cancelar(String id) {
    Optional<PedidoEntity> encontrado = repo.findById(id);
    if (encontrado.isEmpty()) return Optional.empty();

    PedidoEntity entity = encontrado.get();
    if (!"EN_PREPARACION".equals(entity.getEstado())) {
      throw new IllegalStateException("Ya entregado");
    }
    entity.setEstado("CANCELADO");
    repo.save(entity);
    return Optional.of(toResponse(entity));
  }
}
Regla real del negocio (celeste)

Solo 4 líneas expresan la regla: comprobar EN_PREPARACION y pasar el pedido a CANCELADO.

Detalles técnicos pegados (rojo)
  • @Service de Spring.
  • PedidoEntity (@Entity / columnas SQL) y JpaRepository.
  • PedidoResponse (formato de respuesta HTTP).

Constructor e imports omitidos por brevedad. Mientras nada cambie, este código cumple su tarea.

Pide a los estudiantes notar lo familiar que es este código respecto a TareaService.java: funciona, pero mezcla reglas con anotaciones JPA y DTOs HTTP.
El proyecto evoluciona · nuevas demandas

Cuatro cambios frecuentes en un backend Spring Boot

1 · Cambiar persistencia

Migrar de PostgreSQL (JPA) a MongoDB, o incluso reemplazar JPA por JDBC nativo en el mismo PostgreSQL por rendimiento.

2 · Sumar mensajería por eventos

Publicar un aviso en Apache Kafka (topic pedidos-cancelados) cuando se cancele ORD-101, para que inventario y facturación reaccionen.

3 · Cambiar APIs o proveedores

Reembolsos con Stripe → Culqi / Mercado Pago, correos con SendGrid → AWS SES, o comprobantes de disco local a Amazon S3.

4 · Nuevos canales de entrada

Ejecutar la misma cancelación desde una tarea programada (@Scheduled) para pedidos vencidos o un consumidor de eventos, no solo por HTTP.

Apache Kafka es una plataforma de mensajería por eventos donde una aplicación publica avisos en un topic para que otros sistemas los lean sin acoplarse por HTTP. En los cuatro cambios, las reglas de ORD-101, ORD-102 y ORD-999 siguen siendo las mismas.
Amplía la perspectiva: no hace falta migrar de motor de BD para sufrir acoplamiento. Cambiar pasarelas de pago, pasar de disco local a S3 o reutilizar lógica desde @Scheduled pasa todo el tiempo en proyectos reales.
Presión 1 · módulos acoplados

Cambiar de base obliga a editar el servicio de negocio

La operación «cancelar un pedido según su estado» se llama caso de uso. Veamos qué se rompe en el repo actual al reemplazar PostgreSQL/JPA por MongoDB:

1 · PedidoEntity → PedidoDocument

Las anotaciones JPA no aplican a documentos MongoDB.

2 · PedidoRepository cambia

JpaRepository se reemplaza por acceso a MongoDB.

3 · PedidoService se edita

Aunque la regla de ORD-101 y ORD-102 no cambió, hay que tocar el archivo que la contiene.

A esto llamamos acoplamiento: un cambio en una decisión técnica (la base de datos) obliga a modificar los archivos donde vive la lógica de negocio.
Destaca la palabra acoplamiento con el efecto dominó concreto: si la lógica de ORD-101 y ORD-102 no cambió, no debería ser necesario editar su clase por cambiar de BD.
Presión 2 · sumar nuevas tecnologías

En la estructura actual, cada integración termina dentro del servicio

Qué ocurre en service/PedidoService.java al crecer las integraciones
@Service
public class PedidoService {
  private final PedidoRepository repo;       // JPA / SQL
  private final KafkaTemplate<String, String> kafka; // Kafka
  private final StripeClient stripe;          // API pagos

  public Optional<PedidoResponse> cancelar(String id) {
    // ... valida ORD-101 / ORD-102 / ORD-999 y guarda con repo ...
    stripe.refund(entity.getId(), entity.getTotalSoles());
    kafka.send("pedidos-cancelados", entity.getId());
    return Optional.of(toResponse(entity));
  }
}
¿Dónde encajan Kafka, Stripe o S3 en 5 carpetas?

No son controller, ni entity JPA, ni repository SQL. El repositorio actual no separa integraciones externas del negocio.

Un servicio frágil que sabe demasiado

PedidoService mezcla JPA, HTTP DTOs, Kafka y Stripe. Cambiar de Stripe a Culqi o de Kafka a RabbitMQ obliga a editar la misma clase de reglas.

Este síntoma es universal en Spring Boot: cada nuevo SDK (Stripe, SendGrid, S3, Kafka, clientes REST externos) se inyecta directo en el @Service hasta volverlo imposible de mantener.
Presión 3 · costo diario al probar

Probar una regla simple arrastra toda la infraestructura

Supón que solo quieres escribir una prueba JUnit para verificar las reglas de ORD-101, ORD-102 y ORD-999. Al instanciar el servicio actual, el constructor te exige tres tecnologías:

Lo único que queríamos comprobar (Java puro)

Salida 1 · Levantar todo (@SpringBootTest)

Arrancar Spring, PostgreSQL y Kafka tarda varios segundos y falla si falta algún servicio externo, solo para probar una regla en memoria.

Salida 2 · Simular librerías externas

Matiz clave: las pruebas de integración con PostgreSQL y Kafka reales siguen siendo valiosas. La necesidad no es eliminarlas, sino poder probar las reglas de negocio rápido, en Java puro y por separado.
El bloque new PedidoService(???, ???, ???) hace tangible el dolor de inmediato: incluso si nunca cambias de BD, el acoplamiento dificulta probar cada regla día a día. Luego en la diapositiva 25 verán el contraste con new CancelarPedidoService(repoEnMemoria, avisosEnMemoria).

Paso 1 · separar negocio de persistencia

¿Cuál es la diferencia entre Model y Entity?

Model de dominio · domain/model/Pedido
  • Qué representa: el concepto del negocio y sus reglas (cancelar()).
  • Forma: Java puro, sin anotaciones de BD y sin setEstado(...) abierto que permita saltarse reglas.
  • Cuándo cambia: cuando cambia una regla de negocio.
Entity de persistencia · PedidoEntity
  • Qué representa: una fila de tabla SQL en PostgreSQL (@Entity, @Table, @Column, @ManyToOne).
  • Forma: adaptada a Hibernate/JPA (constructor vacío, getters/setters públicos, tipos de columna).
  • Cuándo cambia: cuando cambia el esquema SQL o migras a MongoDB (PedidoDocument).
1 · Negocio sin framework

Si quitamos JPA o pasamos a MongoDB/JDBC, el Model sigue compilando intacto.

2 · Reglas protegidas

La Entity suele exponer setters para Hibernate; el Model obliga a pasar por cancelar().

3 · Esquema desacoplado

Una tabla puede renombrarse o dividirse en dos sin obligar a cambiar la lógica del negocio.

¿Por qué tener el Model si parece duplicar campos? Porque aunque hoy tengan atributos parecidos, tienen razones distintas para cambiar. El costo es un mapper; el beneficio es que la base de datos no dicta tus reglas.
Esta es la pregunta #1 de todo estudiante que viene de Spring Data JPA: «¿por qué crear Pedido si ya tengo PedidoEntity?». Enfatiza los tres motivos: sin anotaciones JPA en el núcleo, encapsulamiento real sin setters abiertos, y libertad para evolucionar tablas o cambiar de BD sin romper reglas.
Paso 1 · el modelo de dominio en código

Así protege las reglas nuestro modelo Pedido

Fragmento Java puro · domain/model/Pedido.java
public enum EstadoPedido { EN_PREPARACION, ENTREGADO, CANCELADO }

public class Pedido {
  private final String id;
  private final int totalSoles;
  private EstadoPedido estado;

  public void cancelar() {
    if (estado != EstadoPedido.EN_PREPARACION) {
      throw new PedidoNoCancelableException(id, estado);
    }
    this.estado = EstadoPedido.CANCELADO;
  }
}

Observa que Pedido no tiene @Entity, ni @Table, ni un setEstado(...) público: la única forma de cancelar pasa por la regla cancelar().
Omitimos constructor y getters por claridad. PedidoNoCancelableException es una RuntimeException simple del dominio. Nota cómo cada recuadro mantiene la identidad del mismo objeto antes y después del evento cancelar().
Paso 1 · dos capas internas del núcleo

Dominio y Aplicación: ¿qué hace cada uno dentro del núcleo?

Dentro del núcleo separamos qué reglas cumple el objeto (Dominio) de en qué orden se ejecuta la operación (Aplicación).

Núcleo · Java puro (sin Spring, JPA, MongoDB ni Kafka)
Aplicación · CancelarPedidoService

«¿En qué orden ocurren los pasos del caso de uso?»

  1. Pide buscar el pedido por id.
  2. Si existe, invoca pedido.cancelar().
  3. Pide guardar el pedido actualizado.
  4. Pide notificar la cancelación.

No hace: no implementa el if de estados ni elige la BD.

paso 2 cancelar()
Dominio · Pedido · EstadoPedido

«¿Es válida esta acción sobre el pedido?»

  • ORD-101 (EN_PREPARACION) → cambia a CANCELADO.
  • ORD-102 (ENTREGADO) → lanza PedidoNoCancelableException y detiene los pasos 3 y 4.

No hace: no busca en BD, no guarda registros ni envía eventos.

Regla práctica: si el código valida una regla propia del pedido (estados, montos, invariantes) va en Dominio; si coordina pasos con el exterior (buscar, guardar, notificar) va en Aplicación.
Refuerza la separación: Pedido nunca inyecta un repositorio. CancelarPedidoService nunca duplica la validación de estados porque delega en pedido.cancelar(). Así varios casos de uso pueden reutilizar la misma regla del dominio.
Paso 1 · fuera del núcleo

Infraestructura: ¿qué vive fuera del núcleo?

Todo lo que depende de Spring, HTTP, bases de datos, Kafka o APIs externas vive en infrastructure. Responde a: «¿con qué tecnología concreta nos conectamos?»

1 · Adaptadores de entrada (adapter/in)

PedidoController (@RestController, rutas HTTP, ResponseEntity), PedidosExpiradosJob (@Scheduled) o consumidores de eventos.

2 · Adaptadores de salida (adapter/out)

PedidoJpaAdapter (@Entity, JpaRepository), PedidoMongoAdapter, PedidoKafkaAdapter, clientes de Stripe, Culqi o S3.

3 · Mappers y DTOs técnicos

Traducen entre el modelo Pedido y formatos externos: PedidoEntity, PedidoDocument, PedidoResponse y PedidoCanceladoEvent.

4 · Configuración y cableado (config)

Clases @Configuration y @Bean de Spring Boot que ensamblan el núcleo con los adaptadores activos y sus propiedades.

Lo que NO hace Infraestructura: nunca decide reglas de negocio (como si ORD-102 puede cancelarse). Regla de dependencia: infrastructure importa application y domain, nunca al revés.
Con esto cerramos las tres grandes capas (domain, application, infrastructure). Destaca que infraestructura es la capa más cambiante: migrar de PostgreSQL a MongoDB o pasar de Stripe a Culqi ocurre aquí sin tocar el núcleo.
Paso 2 · contratos en el borde del núcleo

El puerto de entrada declara la operación disponible

Contrato Java · application/port/in/CancelarPedidoUseCase.java
package com.tienda.pedidos.application.port.in;

import com.tienda.pedidos.domain.model.Pedido;
import java.util.Optional;

public interface CancelarPedidoUseCase {
  Optional<Pedido> cancelar(String id);
}

Un puerto es un contrato en la frontera del núcleo.

El puerto de entrada nombra qué puede pedir un llamador externo a la aplicación: cancelar un pedido por su ID.

Un solo contrato, varios canales posibles

Hoy lo llama un controlador HTTP (PATCH /pedidos/ORD-101/cancelar). Mañana podría llamarlo un consumidor de Kafka o una tarea programada, sin cambiar el contrato.

Usa solo tipos de Java y del dominio; nunca ResponseEntity ni PedidoResponse. Aquí elegimos una interfaz, aunque no todo puerto exige una interfaz obligatoriamente.

Nota que Optional<Pedido> ya es conocido de spring-introduccion. El contrato habla únicamente el lenguaje del negocio.
Paso 2 · capacidades que necesita el núcleo

Los puertos de salida declaran qué necesita la aplicación

Puerto de salida 1 · persistencia
public interface PedidoRepositoryPort {
  Optional<Pedido> buscarPorId(String id);
  Pedido guardar(Pedido pedido);
}

Solo 2 métodos necesarios (no los ~30 de JpaRepository) y trabaja con Pedido, no con PedidoEntity.

Puerto de salida 2 · notificación de eventos
public interface NotificarPedidoCanceladoPort {
  void notificarCancelacion(Pedido pedido);
}

Expresa la intención del negocio («notificar cancelación»), sin nombrar KafkaTemplate ni el topic.

Confusión frecuente: «puerto de salida» no significa respuesta HTTP. «Entrada» indica quién inicia una llamada hacia el núcleo; «salida» indica una capacidad externa que el núcleo solicita hacia afuera (BD, Kafka, correo, API).
Esta distinción entrada/salida (driving vs driven) evita el malentendido más común al aprender arquitectura hexagonal.
Paso 2 · implementación en el núcleo

CancelarPedidoService depende solo de los puertos

Java puro · application/service/CancelarPedidoService.java
public class CancelarPedidoService implements CancelarPedidoUseCase {
  private final PedidoRepositoryPort pedidos;
  private final NotificarPedidoCanceladoPort notificador;

  public CancelarPedidoService(
      PedidoRepositoryPort pedidos,
      NotificarPedidoCanceladoPort notificador) {
    this.pedidos = pedidos;
    this.notificador = notificador;
  }

  public Optional<Pedido> cancelar(String id) {
    Optional<Pedido> encontrado = pedidos.buscarPorId(id);
    if (encontrado.isEmpty()) return Optional.empty();

    Pedido pedido = encontrado.get();
    pedido.cancelar(); // ORD-102 lanza excepción aquí
    Pedido guardado = pedidos.guardar(pedido);
    notificador.notificarCancelacion(guardado);
    return Optional.of(guardado);
  }
}
Comparación con el servicio anterior
  • Cero @Service ni @Entity.
  • Cero JpaRepository ni PedidoDocument.
  • Cero KafkaTemplate ni PedidoResponse.
Si migramos a MongoDB o cambiamos Kafka por otro mensajero, este archivo no necesita editarse.
Pide comparar mentalmente esta clase con las diapositivas 3 y 6: cada línea ahora expresa intención de negocio pura.

Paso 2 · adaptador web

El controlador traduce HTTP al puerto y el resultado a códigos web

Spring Web · infrastructure/adapter/in/web/PedidoController.java
@RestController
public class PedidoController {
  private final CancelarPedidoUseCase cancelarPedido;

  @PatchMapping("/pedidos/{id}/cancelar")
  public ResponseEntity<PedidoResponse> cancelar(
      @PathVariable String id) {
    try {
      return cancelarPedido.cancelar(id)
          .map(p -> ResponseEntity.ok(PedidoResponse.from(p)))
          .orElseGet(() -> ResponseEntity.notFound().build());
    } catch (PedidoNoCancelableException ex) {
      return ResponseEntity.status(409).build();
    }
  }
}
Traducción del controlador
ORD-101 (Optional con pedido)200 OK + JSON ORD-102 (PedidoNoCancelableException)409 Conflict ORD-999 (Optional.empty())404 Not Found
PedidoResponse es el DTO de la API y vive en el adaptador web. El núcleo nunca decide estados HTTP.

Constructor e imports omitidos por brevedad.

También podría traducirse PedidoNoCancelableException con un @RestControllerAdvice; aquí lo mostramos con try/catch directo para que el recorrido completo sea visible en una sola pantalla.
Reutilizar el núcleo · varios canales de entrada

Un mismo puerto de entrada atiende HTTP, tareas programadas y eventos

Segundo adaptador de entrada · infrastructure/adapter/in/scheduler/PedidosExpiradosJob.java
@Component
public class PedidosExpiradosJob {
  private final CancelarPedidoUseCase cancelarPedido;

  @Scheduled(cron = "0 0 * * * *") // cada hora
  public void cancelarVencidos(List<String> idsVencidos) {
    for (String id : idsVencidos) {
      cancelarPedido.cancelar(id);
    }
  }
}
Tres canales, una sola regla
  • HTTP REST: PedidoController (web / app móvil).
  • Tarea programada: @Scheduled cancela pedidos vencidos sin HTTP.
  • Mensajería: un PedidoKafkaConsumer o un comando CLI.
Como el caso de uso no devuelve ResponseEntity ni PedidoResponse, ningún adaptador tiene que fingir peticiones HTTP ni duplicar los if de ORD-101 y ORD-102.

Esquema simplificado: la consulta de IDs vencidos y manejo de excepciones por ítem se omiten por brevedad.

Este ejemplo hace clic de inmediato: en un servicio acoplado a DTOs HTTP o RequestContext, reutilizar lógica desde un cron @Scheduled suele terminar en código duplicado.
Adaptador de salida · persistencia intercambiable

Cambiar de motor o de librería SQL queda aislado en un adaptador

Adaptador actual · infrastructure/adapter/out/persistence/PedidoJpaAdapter.java
@Repository
public class PedidoJpaAdapter implements PedidoRepositoryPort {
  private final SpringDataPedidoRepository jpaRepo;
  private final PedidoMapper mapper;

  public Optional<Pedido> buscarPorId(String id) {
    return jpaRepo.findById(id).map(mapper::toDomain);
  }

  public Pedido guardar(Pedido pedido) {
    PedidoEntity saved = jpaRepo.save(mapper.toEntity(pedido));
    return mapper.toDomain(saved);
  }
}
¿Qué hace PedidoMapper?

Un mapper traduce los datos de ORD-101 entre Pedido (dominio) y PedidoEntity (JPA).

Dos reemplazos posibles sin tocar el núcleo

MongoDB: PedidoMongoAdapter con PedidoDocument.

Mismo PostgreSQL, más rápido: PedidoJdbcAdapter con SQL nativo si Hibernate se vuelve lento en una consulta crítica.

No desechamos Spring Data JPA: lo confinamos detrás de PedidoRepositoryPort.

Subraya el segundo caso: incluso si tu empresa nunca abandona PostgreSQL, poder cambiar JPA por JDBC o jOOQ en un adaptador sin tocar el dominio es muy valioso.
Cambio 2 resuelto · agregar una tecnología nueva

Kafka entra como un adaptador sin ensuciar el caso de uso

Esquema simplificado · infrastructure/adapter/out/messaging/PedidoKafkaAdapter.java
@Component
public class PedidoKafkaAdapter
    implements NotificarPedidoCanceladoPort {

  private static final String TOPIC = "pedidos-cancelados";
  private final KafkaTemplate<String, PedidoCanceladoEvent> kafka;

  public void notificarCancelacion(Pedido pedido) {
    PedidoCanceladoEvent evento = PedidoCanceladoEvent.from(pedido);
    kafka.send(TOPIC, pedido.id(), evento);
  }
}
Qué queda encapsulado aquí
  • El cliente KafkaTemplate de Spring Kafka.
  • El nombre del topic (pedidos-cancelados).
  • El formato del evento PedidoCanceladoEvent para ORD-101.
Si mañana cambiamos Kafka por RabbitMQ o correo, solo reemplazamos este adaptador. Y si otro sistema enviara cancelaciones desde Kafka, un consumidor sería un nuevo adaptador de entrada llamando a CancelarPedidoUseCase.

Esquema simplificado: omite constructor, imports y manejo de errores de envío.

Conecta directamente con el problema de la diapositiva 6: ahora Kafka tiene un hogar claro (infrastructure/adapter/out/messaging) y no contamina PedidoService.

Ventaja en desarrollo local: mientras desarrollas, puedes usar DiscoLocalAdapter o un doble en memoria para pagos y correos sin gastar cuotas ni depender de credenciales de Stripe o AWS.
Este cuadro muestra por qué los equipos usan hexagonal incluso cuando nunca cambian de base de datos: aislar Stripe/Culqi, S3, correos o APIs externas paga dividendos desde la primera semana.
Diagrama 1 · qué ocurre al ejecutarse

En ejecución, las llamadas viajan y regresan por los puertos

ORD-101 · EN_PREPARACION

Busca → cancelar() → guarda → publica en Kafka → 200 OK.

ORD-102 · ENTREGADO

Busca → cancelar() lanza excepción → no guarda ni publica → 409.

ORD-999 · ausente

Busca → Optional.empty() → no guarda ni publica → 404.

Subraya que estas flechas muestran llamadas en tiempo de ejecución. En la siguiente diapositiva veremos por qué las flechas de dependencia en código apuntan al revés.
Diagrama 2 · dependencias de compilación (import)

En el código fuente, todos los adaptadores apuntan hacia el núcleo

Una dependencia en código significa que una clase necesita importar otro tipo para compilar. Aquí está la diferencia clave con el repositorio en capas:

Antes · capas

PedidoService importa directamente JpaRepository, PedidoEntity y KafkaTemplate.

Ahora · inversión de dependencias

CancelarPedidoService solo usa los puertos. PedidoJpaAdapter, PedidoMongoAdapter y PedidoKafkaAdapter implementan esos puertos apuntando hacia adentro.

Compilación ≠ ejecución: al ejecutarse, el servicio llama al adaptador; al compilar, el servicio solo conoce el puerto. Puedes borrar PedidoJpaAdapter o PedidoKafkaAdapter y el núcleo sigue compilando.
Pregunta rápida al grupo: ¿por qué compila CancelarPedidoService si todavía no escribimos PedidoMongoAdapter? Porque depende únicamente de PedidoRepositoryPort.
Paso 3 · ensamblar las piezas al iniciar

Spring conecta el núcleo puro con los adaptadores activos

Spring Boot · infrastructure/config/PedidoConfig.java
@Configuration
public class PedidoConfig {

  @Bean
  CancelarPedidoUseCase cancelarPedidoUseCase(
      PedidoRepositoryPort pedidos,
      NotificarPedidoCanceladoPort notificador) {
    return new CancelarPedidoService(pedidos, notificador);
  }
}
Sin Spring · construcción manual equivalente
CancelarPedidoUseCase caso = new CancelarPedidoService(
    new PedidoJpaAdapter(...), new PedidoKafkaAdapter(...));
Dos anotaciones nuevas

@Configuration marca una clase de ensamblaje fuera del núcleo.

@Bean indica a Spring cómo crear el objeto e inyectarle los adaptadores activos.

Importante: mantén una sola implementación activa de PedidoRepositoryPort (por ejemplo, activar JPA o MongoDB con @Profile o un único bean); si Spring encuentra dos a la vez, no sabrá cuál inyectar.
Antes usaban @Service en PedidoService. Aquí mostramos por qué @Configuration + @Bean permite mantener CancelarPedidoService sin imports de Spring.
Paso 3 · del repositorio en capas al repositorio hexagonal

Cómo se reorganizan las carpetas en el mismo proyecto Spring

Antes · distribución actual (capas)
com/tienda/pedidos/
├── controller/  PedidoController
├── dto/         PedidoResponse
├── service/     PedidoService ← JPA + Kafka
├── repository/  PedidoRepository (JPA)
└── entity/      PedidoEntity (@Entity)
Los nombres de carpetas hacen visibles las fronteras, pero no crean la arquitectura por sí solos: lo esencial es que domain y application no importen nada de infrastructure.
Después · distribución hexagonal (un solo proyecto)
com/tienda/pedidos/
├── domain/model/
│   └── Pedido · EstadoPedido · PedidoNoCancelableException
├── application/
│   ├── port/in/    CancelarPedidoUseCase
│   ├── port/out/   PedidoRepositoryPort · NotificarPedidoCanceladoPort
│   └── service/    CancelarPedidoService
└── infrastructure/
    ├── adapter/in/web/          PedidoController · PedidoResponse
    ├── adapter/in/scheduler/    PedidosExpiradosJob (@Scheduled)
    ├── adapter/out/persistence/ PedidoJpaAdapter · PedidoEntity · Mapper
    ├── adapter/out/messaging/   PedidoKafkaAdapter · PedidoCanceladoEvent
    ├── adapter/out/payment/     StripeAdapter (o CulqiAdapter)
    └── config/                  PedidoConfig (@Configuration)
Conecta directamente con los paquetes reales de spring-introduccion. Señala dónde aterriza Kafka (adapter/out/messaging) y dónde aterriza MongoDB (adapter/out/persistence).
Paso 4 · recompensa inmediata al probar

Probamos ORD-101, ORD-102 y ORD-999 en milisegundos con dobles en memoria

Prueba unitaria JUnit · CancelarPedidoServiceTest.java
@Test
void rechazaEntregadoSinGuardarNiNotificar() {
  RepositorioPedidosEnMemoria repo = new RepositorioPedidosEnMemoria();
  NotificadorEnMemoria avisos = new NotificadorEnMemoria();
  repo.guardar(new Pedido("ORD-102", 85, ENTREGADO));

  CancelarPedidoUseCase caso = new CancelarPedidoService(repo, avisos);

  assertThrows(PedidoNoCancelableException.class,
      () -> caso.cancelar("ORD-102"));
  assertEquals(ENTREGADO, repo.buscarPorId("ORD-102").get().estado());
  assertTrue(avisos.idsNotificados().isEmpty());
}

Un doble de prueba (fake) implementa un puerto en memoria (Map o List) para controlar entradas y observar salidas sin infraestructura.

CasoQué verificamos
ORD-101Queda CANCELADO, guardado y registrado en avisos.
ORD-102Lanza excepción; estado sigue ENTREGADO; avisos vacío.
ORD-999Devuelve Optional.empty(); nada guardado ni notificado.

Sin arrancar Spring, sin PostgreSQL, sin MongoDB y sin broker Kafka.

Recuerda que JUnit (@Test, assertThrows, assertEquals) se vio en la lección de POO. Nota que esta prueba valida una regla crítica: un pedido entregado nunca dispara un evento falso hacia Kafka.
Paso 4 · lo que las pruebas unitarias NO cubren

Integración comprueba JPA, MongoDB, Kafka y HTTP reales

Un doble en memoria confirma la lógica del núcleo, pero no demuestra que una consulta SQL, un documento MongoDB o un envío a Kafka funcionen de verdad.

Tipo de pruebaQué piezas ejecutaQué errores detecta
Unitaria del núcleo Pedido + CancelarPedidoService + dobles en memoria Reglas rotas (por ejemplo, cancelar ORD-102 o notificar cuando falla).
Integración de adaptador BD PedidoJpaAdapter o PedidoMongoAdapter + BD real/de prueba Columnas mal mapeadas en PedidoMapper, anotaciones @Entity, ausencia de ORD-999.
Integración de mensajería PedidoKafkaAdapter + broker Kafka de prueba Error de serialización de PedidoCanceladoEvent o nombre incorrecto del topic.
Prueba HTTP (web) PedidoController + Spring Web Ruta mal escrita, JSON incompleto o códigos 200 / 409 / 404 incorrectos.
Cada nivel aporta evidencia distinta: las pruebas unitarias rápidas complementan —no reemplazan— a las de integración.
Evita vender las pruebas unitarias como garantía total: si PedidoMapper mapea mal una columna o el estado, solo una prueba sobre el adaptador/mapper lo atrapa.
Realismo técnico · límites de la arquitectura

Cambiar un adaptador ayuda, pero no resuelve toda la migración

Reemplazar adaptador
PedidoJpaAdapter → PedidoMongoAdapter
≠
Migrar datos y operación
trasladar registros, configurar Kafka y validar producción
1 · Migrar registros

Copiar pedidos existentes de PostgreSQL a MongoDB y verificar que ORD-101 y ORD-102 conserven exactamente sus valores.

2 · Infraestructura real

Configurar índices en MongoDB, crear el topic pedidos-cancelados en Kafka, credenciales, reintentos y monitoreo.

3 · Fallos técnicos

Una caída de BD o de Kafka es un error técnico, nunca un Optional.empty() («pedido ausente»).

La arquitectura hexagonal reduce el riesgo de tocar las reglas de negocio durante el cambio, pero el trabajo de datos y operación sigue siendo imprescindible.
Honestidad profesional: cambiar de base de datos o introducir Kafka en producción conlleva migración de datos, consistencia (por ejemplo, qué pasa si guarda en BD y falla Kafka) y configuración operativa.
Criterio de ingeniería · beneficios y costos

Cuándo basta con capas y cuándo compensa hexagonal

CriterioCapas (controller / service / repository / entity)Arquitectura hexagonal (puertos y adaptadores)
Complejidad inicial Menor: menos archivos y arranque muy rápido. Mayor: puertos, Pedido separado de PedidoEntity, mappers y @Bean.
Cambiar BD o sumar Kafka Impacta service y mezcla tecnologías junto a reglas. Cambios localizados en nuevos adaptadores; núcleo intacto.
Probar reglas de negocio Suele arrastrar JpaRepository, Spring o mocks complejos. Pruebas unitarias rápidas en Java puro con dobles en memoria.
Cuándo encaja mejor CRUD sencillo, pocas reglas, persistencia estable, prototipos. Reglas clave, múltiples canales o integraciones cambiantes (BD, Kafka, APIs).
No agregues puertos ni mappers por cumplir un diagrama. Adopta estas fronteras donde realmente necesites aislar reglas de cambios externos.
Refuerza criterio adulto: ambas arquitecturas son herramientas válidas según el contexto y el ciclo de vida del repositorio.
Resumen · volver a los cuatro cambios del repositorio

Las reglas de ORD-101 y ORD-102 permanecen; las tecnologías cambian en los bordes

Intacto en el núcleo

Pedido.cancelar() y CancelarPedidoService sin imports externos.

Persistencia

Reemplazas PedidoJpaAdapter por MongoDB o JDBC nativo tras el mismo puerto.

Integraciones

Sumas o cambias Kafka, Stripe/Culqi, correo o S3 como adaptadores de salida.

Entradas

HTTP, @Scheduled o un consumidor Kafka reutilizan el mismo puerto.

Comprueba 1: ¿Por qué separamos Pedido de PedidoEntity?

Para que JPA no contamine las reglas al migrar de BD o pasar a JDBC.

Comprueba 2: ¿Hacia dónde apunta la dependencia de un adaptador?

Hacia adentro: cada adaptador implementa un puerto del núcleo.

Comprueba 3: ¿Qué NO prueban los dobles en memoria?

Mapeos SQL/Mongo, envío real a Kafka, pasarelas externas ni HTTP.

Práctica · sin solución completa

Prepara un caso de uso para cambiar tecnologías sin tocar sus reglas

Objetivo

Refactorizar «cancelar pedido» (o «completar tarea» de spring-introduccion) separando domain, PedidoRepositoryPort, NotificarPedidoCanceladoPort y el servicio de aplicación, y validarlo con dobles en memoria.

Punto de partida

Un servicio en capas acoplado a Entity, JpaRepository y clientes externos, con los casos ORD-101 (EN_PREPARACION), ORD-102 (ENTREGADO) y ORD-999 (ausente).

Resultado esperado

Pruebas unitarias JUnit que verifiquen: ORD-101 queda CANCELADO, guardado y notificado; ORD-102 lanza excepción sin guardar ni notificar; ORD-999 devuelve vacío sin guardar ni notificar.

Restricciones

Cero imports de Spring, JPA, MongoDB, Kafka ni clientes HTTP en domain y application. Las pruebas unitarias no deben conectarse a infraestructura real.

Desafío opcional: implementa y cablea con @Configuration / @Bean al menos dos adaptadores reales o simulados —por ejemplo PedidoJpaAdapter + un segundo adaptador a elección (PedidoKafkaAdapter, un job @Scheduled o un ProcesarReembolsoPort para Stripe/Culqi).
Los alumnos pueden aplicar el mismo patrón directamente sobre TareaService.completarTarea de spring-introduccion o sobre el ejercicio del gimnasio si prefieren practicar en su propio repositorio.
