Punto de partida técnico

El servicio consulta directamente PostgreSQL

Dentro de ConsultarPedidoService · fragmento de éxito
Pedido buscar(String id) {
  String sql =
      "SELECT * " +
      "FROM pedidos WHERE id = ?";
  Map<String, Object> fila = jdbc.queryForMap(sql, id);
  return new Pedido(
      (String) fila.get("id"),
      (int) fila.get("cantidad"),
      (int) fila.get("precio_soles"),
      (int) fila.get("total_soles"),
      (String) fila.get("estado"));
}

SQL es un lenguaje para consultar datos relacionales; ? recibe el ID como parámetro.

JdbcTemplate es una ayuda de Spring. Aquí jdbc lo representa; la fila se recibe como un mapa de nombres de columna a valores.

El código funciona. Mostramos solo el caso exitoso y suponemos columnas de enteros para cantidad y soles; omitimos conexión, imports y tratamiento de ausencia.

2 · Lectura

Columnas de la fila: sustituir por campos del documento.

La tarea sigue siendo buscar A-17, pero hoy el servicio debe editarse porque contiene esos detalles de persistencia.

Implementación de la aplicación

El servicio recibe el puerto de salida

Fragmento Java · implementación del caso de uso
final class ConsultarPedidoService
    implements ConsultarPedido {
  private final BuscarPedido pedidos;

  ConsultarPedidoService(BuscarPedido pedidos) {
    this.pedidos = pedidos;
  }

  public Optional<Pedido>
      buscarPorId(String id) {
    return pedidos.buscarPorId(id);
  }
}

Un constructor prepara una instancia al recibir sus dependencias.

Inyección por constructor significa que quien crea el servicio le suministra el colaborador BuscarPedido.

No se necesita un framework para esta relación. El servicio coordina la capacidad requerida y no importa una clase de base de datos.
Una implementación realista en su límite

El adaptador convierte fila SQL a Pedido

Fragmento Java · encontrado o ausente
final class PedidoPostgresAdapter
    implements BuscarPedido {
  public Optional<Pedido>
      buscarPorId(String id) {
    List<Pedido> filas = jdbc.query(
      "SELECT * " +
      "FROM pedidos WHERE id = ?", mapper, id);
    return filas.stream().findFirst();
  }
}

mapper es un conversor: lee los cinco campos de cada fila y crea un Pedido, como en el ejemplo anterior.

findFirst() devuelve el primer pedido de la lista, o ausencia si está vacía. El ID debe identificar una sola fila.

Omitimos campos, constructor y configuración de jdbc y mapper. La consulta SQL queda dentro del adaptador, no del servicio.
Mismo contrato · otra traducción

El adaptador Mongo mapea campos a Pedido

Pseudocódigo Java · acceso al driver omitido
final class PedidoMongoAdapter
    implements BuscarPedido {
  public Optional<Pedido>
      buscarPorId(String id) {
    documento = coleccion.findOne("id", id);
    if (documento == null) {
      return Optional.empty();
    }
    return Optional.of(new Pedido(
      documento.getString("id"),
      documento.getInteger("cantidad"),
      documento.getInteger("precioSoles"),
       documento.getInteger("totalSoles"),
       documento.getString("estado")));
  }
}

Un driver permite comunicarse con MongoDB; una colección agrupa documentos relacionados.

Este pseudocódigo supone que no encontrar un documento devuelve null. No es la sintaxis de un driver concreto; el ID debe ser único.

El adaptador convierte los campos a Pedido y la ausencia a Optional.empty(). Ningún documento sale hacia el núcleo.
Traducir de vuelta al contrato web

El controlador transforma el resultado a HTTP

Fragmento Spring Web · dentro de PedidoController
@GetMapping("/pedidos/{id}")
public ResponseEntity<Pedido> consultar(
    @PathVariable("id") String id) {
  Optional<Pedido> pedido =
      servicio.buscarPorId(id);
  if (pedido.isEmpty()) {
    return ResponseEntity.notFound().build();
  }
  return ResponseEntity.ok(pedido.get());
}

{id} es la parte variable de la ruta. @PathVariable pasa su valor al argumento: A-17 o A-99.

ResponseEntity es un tipo de Spring para respuestas HTTP. Aquí Spring convierte los cinco campos del pedido a JSON.

Omitimos imports, anotación de clase y constructor. servicio es el puerto ConsultarPedido. El núcleo no usa tipos HTTP.
Elegir implementación

El cableado conecta contratos y objetos concretos

Pseudocódigo · construcción manual
BuscarPedido salida = new PedidoPostgresAdapter(...);
ConsultarPedido caso =
    new ConsultarPedidoService(salida);
PedidoController http =
     new PedidoController(caso);
Esquema Spring · ... omite dependencias
@Configuration
class Config {
  @Bean BuscarPedido buscarPedido(...) {
    return new PedidoPostgresAdapter(...);
  }
}

Spring puede crear objetos y suministrar dependencias: @Configuration agrupa configuración y @Bean declara un objeto administrado.

Registra una sola implementación activa de BuscarPedido para este caso. Si hay varias, selecciona una de forma explícita. La configuración queda fuera del núcleo.

Comprobar sin infraestructura

Un doble de prueba controla la salida del puerto

Fragmento Java · dentro de un método de prueba
Pedido pedidoA17 = new Pedido(
    "A-17", 3, 12, 36, "EN_PREPARACION");
BuscarPedido falso = id -> Optional.of(pedidoA17);
ConsultarPedido servicio =
    new ConsultarPedidoService(falso);

boolean coincide = servicio.buscarPorId("A-17")
    .equals(Optional.of(pedidoA17));
System.out.println(coincide); // true

Un doble de prueba sustituye una dependencia para controlar lo que devuelve.

id -> ... es una función breve de Java: implementa el único método del puerto. Este doble devuelve siempre A-17.

Solo comprobamos que el servicio devuelve el resultado recibido. No demostramos búsqueda por ID ni mapeo correcto. No iniciamos Spring ni una base.

Beneficios y costos

Los límites tienen un costo y un propósito

Puede ayudar cuando

Existen límites de responsabilidad claros, alternativas concretas de integración o necesidad de probar la aplicación aislada.

También cuesta

Más contratos, mapeos y cableado que mantener. Una API con pocas operaciones sencillas puede necesitar menos estructura.

Si un componente de acceso a datos ya oculta bien la persistencia, puede que ya tengas una frontera útil. No agregues capas por cumplir un dibujo.

Práctica · sin solución completa

Comprueba el caso de uso antes de cambiar su adaptador

Objetivo y punto de partida

Con los contratos ConsultarPedido, BuscarPedido, servicio y Pedido de esta lección, implementa un doble de prueba en memoria.

Resultado observable

Buscar A-17 devuelve sus 3 cuadernos, S/ 12 y total S/ 36; buscar A-99 devuelve ausencia.

Restricciones

No edites el núcleo, no conectes base ni Spring. El doble debe implementar BuscarPedido.

Entrega y desafío

Muestra ambas comprobaciones. Opcional: enumera qué trabajo de datos y configuración faltaría para MongoDB.

La prueba reduce incertidumbre del caso de uso, pero no demuestra que el adaptador Postgres o Mongo consulte y mapee bien.
